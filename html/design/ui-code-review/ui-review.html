ui-review

combined

The two copies describe different review procedures. The davepoon copy is a thin wrapper that delegates to an external workflow file and produces a 6-pillar graded audit (1-4 per pillar) in a UI-REVIEW.md file. The sickn33 copy is a self-contained checklist covering 8 specific areas (design tokens, component conventions, a11y, mobile, performance, typography, spacing, coherence) with a Pass/Needs Improvement/Fail output format. They overlap in the general goal of reviewing UI code, but the sickn33 copy contains material steps and constraints (specific checklists, output format, when-not-to-use guidance) that the davepoon copy lacks, and the davepoon copy has a different output artifact and grading scale. Crowning one would hide a real alternative procedure.

# UI Design Review

## When to Use
Use this skill when you need to review UI code for design system compliance, accessibility, and best practices.

## When NOT to Use
- For accessibility-only issues → use a dedicated a11y skill
- For Nielsen UX heuristics → use a dedicated audit skill
- For a quick automated check → use a linter
- For non-UI code (data fetching, business rules)

## Input
Review the file or phase specified in $ARGUMENTS. If no argument is given, default to the last completed phase or the most recently modified UI file.

## Checklist

### 1. Design Token Compliance
- [ ] No hardcoded hex colors (use semantic tokens: `text-foreground`, `bg-brand`, etc.)
- [ ] No hardcoded px spacing in Tailwind (use `p-6` not `p-[24px]`)
- [ ] Shadows use CSS variables (`shadow-[var(--shadow-card)]`)
- [ ] Border radius follows the scale (`rounded-md`, `rounded-lg`, `rounded-2xl`)

### 2. Component Conventions
- [ ] Uses `data-slot` attribute
- [ ] Uses `cn()` for className merging
- [ ] Props typed with `React.ComponentProps<>`
- [ ] Supports `className` prop override
- [ ] Named export (not default export for components)
- [ ] No wrapper components that only add a className

### 3. Accessibility (a11y)
- [ ] Touch targets >= 44x44px for interactive elements
- [ ] `focus-visible` styles on all interactive elements
- [ ] Proper `aria-*` attributes where needed
- [ ] Color contrast meets WCAG AA (4.5:1 for text, 3:1 for large text)
- [ ] Animations respect `prefers-reduced-motion`
- [ ] Images have `alt` text
- [ ] Form inputs have associated labels

### 4. Mobile Best Practices
- [ ] No horizontal overflow
- [ ] Touch-friendly spacing between interactive elements
- [ ] Safe area insets handled for notched devices
- [ ] Text sizes >= 12px for readability
- [ ] Scrollable containers have `-webkit-overflow-scrolling: touch`

### 5. Performance
- [ ] No unnecessary re-renders (stable references, memoization where needed)
- [ ] Images are lazy-loaded
- [ ] Heavy components are code-split

### 6. Typography
- [ ] Uses the project's font stack
- [ ] Font sizes from the defined scale
- [ ] Proper font weights (400, 500, 600, 700)
- [ ] Display text: `leading-none` + `tracking-[-0.02em]`
- [ ] Heading text: `leading-snug` + `tracking-[-0.01em]`
- [ ] Body text: `leading-normal` (no custom tracking)
- [ ] Caption uppercase: `tracking-[0.05em]` or `tracking-wide`
- [ ] No `line-height: 1.5` on display/heading text

### 7. Spacing Consistency
- [ ] All spacing values are multiples of the base unit (e.g. 6px)
- [ ] No arbitrary spacing values
- [ ] Uses `size-*` shorthand instead of `w-* h-*`
- [ ] Uses `ms-*/me-*` instead of `ml-*/mr-*` (logical properties)
- [ ] Motion transitions use design tokens

### 8. Coherence
- [ ] One radius personality applied system-wide
- [ ] One accent color for interactive emphasis
- [ ] No emoji as UI icons
- [ ] Status color = severity, not decoration
- [ ] No decorative hues
- [ ] One shadow language
- [ ] One icon family / fill mode / stroke weight
- [ ] Nested-radius law: inner = outer − padding
- [ ] Consistent control heights
- [ ] Errors/states never rely on color alone

## Output Format
Provide:
1. **Score**: Pass / Needs Improvement / Fail
2. **Issues**: List each violation with file:line reference
3. **Fixes**: Concrete code changes for each issue

## Limitations
- Use this skill only when the task clearly matches the project context.
- Verify commands, generated code, dependencies, and external service behavior before applying changes.
- Do not treat examples as a substitute for environment-specific tests, security review, or user approval for destructive or costly actions.
