# Design Critique

## Choose the mode
- **Team facilitation** — use when running a live session with people in the room.
- **Solo expert review** — use when asked to critique a design, UI, Figma file, wireframe, or user flow and produce a written report.
- **Visual analysis** — use when given an image, screenshot, logo, photo, graphic, or PDF and asked for theory-backed feedback.

## Team facilitation (live session)
### Before the critique
- Designer shares context: goals, constraints, target audience, stage of work.
- Define what feedback is needed (layout, flow, copy, everything).
- Set the rules: constructive, specific, actionable.

### During the critique
1. **Present** (5 min) — Designer walks through the work and goals.
2. **Clarify** (5 min) — Questions to understand, not judge.
3. **Feedback rounds** — Structured by category or priority.
4. **Discuss** — Open conversation on key tensions.
5. **Capture** — Document decisions and action items.

### Feedback format
- "I notice..." (observation, not judgment)
- "I wonder..." (question or exploration)
- "What if..." (suggestion or alternative)
- "I think... because..." (opinion with rationale)

### After the critique
- Designer summarizes takeaways.
- Action items with owners and deadlines.
- Follow-up review if needed.

### Critique types
- **Desk crit**: Informal, 1-on-1, quick feedback.
- **Team crit**: Scheduled, structured, full team.
- **Cross-team crit**: Fresh eyes from outside the project.
- **Stakeholder review**: Decision-focused, approval-oriented.

### Common pitfalls
- Designing by committee (too many opinions, no direction).
- Focusing on personal preference instead of user needs.
- Critiquing too early (exploring) or too late (polishing).
- No clear next steps.

### Best practices
- Separate exploration critiques from refinement critiques.
- Critique the work, not the person.
- Always tie feedback to goals and user needs.
- Rotate the facilitator role.
- Make critique a regular ritual, not an event.

## Solo expert review (written report)
### Required inputs
Work from what is given. If any input is missing, fill the gap with a reasonable assumption marked *(assumed, confirm)* and list assumptions at the end. Ask a question first only when the core subject itself is missing.
- **What is being reviewed** (screen, flow, component, full product)
- **Design description or attached image**
- **User goal** (what is the user trying to accomplish?)
- **Context** (web / mobile / desktop app / physical product)
- **Stage** (early wireframe / mid-fidelity / high-fidelity / live product)
- **Primary concern** (optional)

### Output structure
# Design Critique: [Design Name or Screen]
**User goal:** [What the user needs to accomplish]
**Context:** [Platform / Stage]
**Critique focus:** [Primary concern if stated, otherwise "full review"]

## 1. What's Working
3–5 specific, honest observations about genuine strengths. Be specific; do not manufacture praise.

## 2. Priority Issues
Rank issues by impact on the user goal:
- 🔴 **High** — Blocks or significantly degrades the user's ability to complete their goal.
- 🟡 **Medium** — Causes friction or confusion but doesn't block completion.
- 🟢 **Low** — Polish or preference.

For each issue include:
- **What's happening:** Specific design problem.
- **Why it matters:** Connection to user goal or principle.
- **Framework reference:** Name the principle violated (e.g. Nielsen's Heuristic #6, Gestalt proximity, JTBD clarity, Fitts's Law).
- **Recommendation:** Specific, actionable suggestion.

## 3. Heuristic Assessment
Score each relevant Nielsen heuristic as ✅ Pass / 🟡 Partial / ❌ Fail:
| Heuristic | Status | Note |
|---|---|---|
| 1. Visibility of system status | | |
| 2. Match between system and real world | | |
| 3. User control and freedom | | |
| 4. Consistency and standards | | |
| 5. Error prevention | | |
| 6. Recognition rather than recall | | |
| 7. Flexibility and efficiency of use | | |
| 8. Aesthetic and minimalist design | | |
| 9. Help users recognise, diagnose, and recover from errors | | |
| 10. Help and documentation | | |
Only include heuristics relevant to what's visible.

## 4. Gestalt Principles Check
Comment on well-applied or violated principles:
- **Proximity:** Are related elements grouped clearly?
- **Similarity:** Do similar elements look similar?
- **Continuity:** Does the eye flow naturally?
- **Figure/Ground:** Is primary content clearly distinguished from background?
- **Closure:** Are any implied shapes or containers confusing?

## 5. JTBD Alignment
- Does the design make the user's primary job obvious?
- Are there elements that distract from the primary job?
- What emotional job does this design serve, and does the visual design match it?

## 6. Top 3 Recommended Next Steps
Prioritised list of the 3 most impactful, actionable changes.

### Quality checks
- "What's working" includes only genuine, specific observations.
- Every issue has a framework reference.
- Recommendations are specific and actionable.
- Priority levels reflect actual impact on user goal.
- Heuristic assessment only covers visible elements.

### Anti-patterns
- Do not lead with visual preference; every issue must reference a UX principle or user impact.
- Do not invent problems in "What's Working."
- Do not assign the same priority level to every issue.
- Do not skip the JTBD section for product screens.

## Visual analysis (image-based)
### Input
Any visual file — UI design, logo, photo, graphic, PDF exported as image, Figma frame.

### Analysis frameworks
Examine the visual through 11 dimensions:
1. **Gestalt Principles** — proximity, similarity, continuity, closure, figure/ground, common fate, prägnanz, uniform connectedness.
2. **Visual Hierarchy** — focal point, reading paths, size, weight, colour, position, whitespace.
3. **Colour Science (Itten)** — contrast types, harmony systems, emotional temperature, WCAG contrast (4.5:1 text, 3:1 UI), colourblind accessibility.
4. **Typography** — type scale coherence, font pairings, readability (16px+ body), line length (45–75 chars), line height (1.5+), hierarchy through type.
5. **Grid Structure & Alignment (Müller-Brockmann)** — underlying grid, alignment consistency, modulation, spacing rhythm, margins and gutters.
6. **Composition & Moment (Freeman)** — viewpoint, framing, depth relationships, focus and blur, scale and proportion.
7. **Information Design (Tufte)** — data-ink ratio, information density, layering, progressive disclosure, cognitive load.
8. **Reduction & Honesty (Rams/Bauhaus)** — nothing superfluous, form follows function, reduction to essentials, timelessness, honest representation.
9. **Visual Balance & Weight** — symmetrical vs asymmetrical balance, visual weight, tension, composition stability.
10. **Usability Heuristics (Nielsen/Norman)** — system visibility, match to real world, user control, consistency, error prevention and recovery, recognition vs recall, flexibility and efficiency, aesthetic and minimalist design, error messages, help and documentation.
11. **Platform Conventions** — web, mobile, social, print, email norms, safe zones, thumb-friendliness, expected patterns.

### Output format — priority-ordered action list
Group findings by severity. **Hard rule:** every finding must include a `Fix:` line.

#### 🔴 Critical
Issues that break usability, accessibility, or core functionality. Fix immediately.

#### 🟡 Important
Issues that hurt the experience or violate design principles without breaking core function. Fix soon.

#### 🟢 Polish
Issues that elevate the design or address missed opportunities. Fix when time allows.

For each finding include:
- Description of the issue.
- Which framework or principle is violated.
- **Fix:** Specific, actionable correction.
