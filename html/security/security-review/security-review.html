# Security Review

Guide the user through a security review. The procedure adapts to the target:

- **Power Pages site**: Run the focused sub-skills (scan-code, scan-site,
  manage-headers, manage-firewall, audit-permissions, setup-auth) and
  assemble every finding into a single HTML report at
  `<PROJECT_ROOT>/docs/security-review-<YYYY-MM-DD-HHMMSS>.html`.
- **Code or design/PR**: Perform a focused pass over the recurring risk
  areas and produce a severity-ranked table with a ship / fix-first / block
  verdict.

## Workflow

1. **Prerequisites**
   - For Power Pages: locate `powerpages.config.json`; for live-site goals
     confirm `.powerpages-site/website.yml` exists. Create a temporary
     working folder under `<SYSTEM_TEMP>/security-review/`.
   - For code/design: confirm the user owns or is authorized to review the
     target. Capture the stack, data/permissions touched, and sensitivity.

2. **Scope**
   - Ask the user what to review (code & config, release readiness, deployed
     site, or a specific design/PR). If the initial request already answers
     it, skip.

3. **Research before flagging**
   - For each potential issue, trace the data flow to confirm the input is
     attacker-controlled. Check for validation, sanitization, framework
     protections, and server-controlled configuration. Do not report based
     solely on pattern matching.

4. **Run checks**
   - Power Pages: run the matching sub-skills in review mode.
   - Code/design: scan each risk area:
     1. AuthN / AuthZ (incl. IDOR, privilege escalation)
     2. Input handling (injection, SSRF, path traversal, deserialization, XSS)
     3. Secrets & crypto
     4. Data exposure
     5. Dependencies & config
     6. Abuse & availability

5. **Report**
   - Power Pages: build the consolidated HTML report with totals and
     per-section findings.
   - Code/design: produce a severity-ranked table:

     | Severity | Area | Finding (how it's exploited) | Fix |
     |---|---|---|---|
     | Critical/High | | | |
     | Medium | | | |
     | Low / hardening | | | |

   - Include a one-line summary and a verdict: ✅ ship / 🔁 fix-first / ⛔
     block, naming the gating issues.
   - Acknowledge existing good controls and flag follow-ups (scanner,
     pentest, deeper look).

6. **Cleanup**
   - Remove temporary files created during the review.

## Confidence Levels (code/design)

| Level | Criteria | Action |
|-------|----------|--------|
| HIGH | Vulnerable pattern + attacker-controlled input confirmed | Report with severity |
| MEDIUM | Vulnerable pattern, input source unclear | Note as "Needs verification" |
| LOW | Theoretical, best practice, defense-in-depth | Do not report |

## Do Not Flag

- Test files (unless explicitly reviewing test security)
- Dead code, commented code, documentation strings
- Patterns using constants or server-controlled configuration
- Code paths that require prior authentication (note the auth requirement)
- Framework-mitigated patterns (e.g., Django auto-escaping, React
  auto-escaping, ORM parameterized queries) unless the mitigation is
  explicitly bypassed.

## Conflicts

- **microsoft/power-platform-skills**: Produces an HTML report; does not
  produce a severity-ranked table or ship/fix-first verdict.
- **getsentry/skills**: Reports only HIGH CONFIDENCE findings; does not
  produce an HTML report or ship/fix-first verdict.
- **mohitagw15856/pm-claude-skills**: Produces a severity-ranked table and
  ship/fix-first/block verdict; does not run sub-skills or produce an HTML
  report.

## Quality Checks

- [ ] Every standard risk area is considered
- [ ] Findings are ranked by severity with a concrete, actionable fix each
- [ ] Exploitability is explained — why it's a real issue in this context
- [ ] A clear verdict names the gating issues
- [ ] Existing good controls are acknowledged
- [ ] Deeper follow-ups (scanner/pentest) are flagged

## Anti-Patterns

- [ ] Do not produce a generic checklist — tie each finding to this
  code/design and its exploit path
- [ ] Do not rank everything the same — separate critical from hardening nits
- [ ] Do not report an issue without a fix
- [ ] Do not miss authorization (IDOR/privilege)
- [ ] Do not review code you don't own or aren't authorized to assess
