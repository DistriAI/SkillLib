# API Design Principles

## When to Use
- Designing new REST or GraphQL APIs.
- Refactoring existing APIs for better usability.
- Establishing API design standards.
- Reviewing API specifications before implementation.

## Instructions

1. **Define Consumers and Constraints**
   - Identify consumer types (web, mobile, partners, internal).
   - Capture constraints: latency, throughput, consistency, compliance, and data sensitivity.

2. **Choose API Style and Boundaries**
   - **REST**: Best for resource-oriented CRUD, cacheable reads, and simple endpoints.
   - **GraphQL**: Best for multiple clients with varying data shapes and frequent iteration.
   - If mixing, define clear boundaries (e.g., GraphQL for read aggregation, REST for writes).

3. **Model Resources and Types**
   - **REST**: Use nouns for resources, stable identifiers, and consistent naming. Map operations to HTTP verbs (GET, POST, PUT, PATCH, DELETE).
   - **GraphQL**: Define types and field ownership. Use Query for reads, Mutation for writes, and Input types for complex arguments.

4. **Specify Cross-Cutting Concerns**
   - **Errors**: Define a consistent error model (code, message, details, requestId). Use appropriate HTTP status codes.
   - **Pagination**: Choose between offset-based or cursor-based pagination. Define filtering and sorting rules.
   - **Versioning**: Choose a strategy (URL, Header, or Query Parameter) and define a deprecation plan.
   - **Auth & Security**: Define authentication (e.g., Bearer tokens) and authorization scopes. Consider idempotency keys for write operations.

5. **Validate and Review**
   - Create request/response examples (e.g., using `curl` or code snippets).
   - Review for consistency in naming, error handling, and pagination.
   - Check for risks or gaps in the contract.

## Resources
- Refer to specific implementation playbooks or checklists for detailed patterns if available in the local context.
