# React Patterns

Use this skill when writing new React components, reviewing code for performance or architecture issues, or refactoring components that feel slow or tangled.

## 1. Scope and Approach

- Apply the rules as a checklist for new components, a review guide for existing code, or a refactoring playbook for slow or tangled components.
- Profile before optimizing. Use React DevTools Profiler to confirm a bottleneck before applying a fix.
- If the project uses Vite + Cloudflare Workers, prioritize the Vite-specific bundle and waterfall rules below.

## 2. Eliminating Waterfalls (CRITICAL)

Sequential async calls where they could be parallel are the top performance killer.

- Await in sequence: replace `const a = await getA(); const b = await getB();` with `const [a, b] = await Promise.all([getA(), getB()]);`.
- Fetch in child: hoist fetches to the highest common ancestor and pass data down.
- Suspense cascade: use one Suspense boundary wrapping all async siblings instead of multiple boundaries that resolve sequentially.
- Await before branch: move the await inside the branch so you do not fetch data you might not use.
- Import then render: use `React.lazy()` + `<Suspense>` instead of awaiting a dynamic import before rendering.

How to find them: search for `await` in components. If two awaits are independent, they should be parallel.

## 3. Bundle Size (CRITICAL)

- Barrel imports: import directly from the module path instead of a barrel file.
- No code splitting: use `React.lazy(() => import('./HeavyComponent'))` + `<Suspense>` for heavy components.
- Third-party at load: load analytics or tracking after hydration in a `useEffect`.
- Full library import: import only the needed function, e.g. `import debounce from 'lodash/debounce'`.
- Lucide tree-shaking: import explicit icons instead of `import * as Icons from 'lucide-react'`.
- Duplicate React: add `resolve.dedupe: ['react', 'react-dom']` in vite.config.ts.

How to find them: run `npx vite-bundle-visualizer` to inspect the bundle.

## 4. Composition Architecture (HIGH)

- Boolean prop explosion: replace many boolean props with explicit variant components.
- Compound components: split complex components into parent + child components with shared context.
- renderX props: use children and named slots instead of multiple render props.
- Lift state: move shared state to a parent or context provider.
- Provider implementation: expose an interface `{ state, actions, meta }` and hide implementation details.
- Inline components: define child components outside the parent to avoid remounting on every render.

The test: if a component has more than 5 boolean props, it needs composition, not more props.

## 5. Re-render Prevention (MEDIUM)

Only fix re-renders that cause visible jank or wasted computation.

- Default object/array props: hoist default values to module scope.
- Derived state in effect: derive during render with `useMemo` instead of setting state in an effect.
- Object dependency: use primitive dependencies in `useEffect` when possible.
- Subscribe to unused state: split context or use a selector such as `useSyncExternalStore`.
- State for transient values: use `useRef` for values that change frequently but do not need re-render.
- Inline callback props: use `useCallback` or a stable handler reference.

How to find them: use React DevTools Profiler or `<React.StrictMode>` double-renders in dev.

## 6. React 19 Specifics (MEDIUM)

- Use `useActionState` for form submission state.
- Use `useOptimistic` for optimistic UI updates.
- Use `use` to read resources in render.
- Leverage the React Compiler for automatic memoization and reduce manual `useMemo`/`useCallback` where appropriate.

## 7. Component Design Principles

- One responsibility per component.
- Props down, events up.
- Composition over inheritance.
- Prefer small, focused components.
- Classify components as Server, Client, Presentational, or Container based on data fetching and interactivity needs.

## 8. Hook Patterns

- Extract hooks when the same logic is needed in multiple places, e.g. `useLocalStorage`, `useDebounce`, `useFetch`, `useForm`.
- Hooks at top level only.
- Same hook order every render.
- Custom hooks start with `use`.
- Clean up effects on unmount.

## 9. State Management Selection

- Simple state: `useState`, `useReducer`.
- Shared local state: Context.
- Server state: React Query or SWR.
- Complex global state: Zustand or Redux Toolkit.

State placement:
- Single component: `useState`.
- Parent-child: lift state up.
- Subtree: Context.
- App-wide: global store.

## 10. Performance Principles

- Slow renders: profile first.
- Large lists: virtualize.
- Expensive calculation: `useMemo`.
- Stable callbacks: `useCallback`.

Optimization order:
1. Check if actually slow.
2. Profile with DevTools.
3. Identify bottleneck.
4. Apply targeted fix.

## 11. Error Handling

- App-wide error boundary at the root level.
- Feature-level error boundary at the route or feature level.
- Component-level error boundary around risky components.

Error recovery:
- Show fallback UI.
- Log the error.
- Offer a retry option.
- Preserve user data.

## 12. TypeScript Patterns

- Use `interface` for component props.
- Use `type` for unions and complex types.
- Use generics for reusable components.
- Use `ReactNode` for children, `MouseEventHandler` for event handlers, and `RefObject<Element>` for refs.

## 13. Testing Principles

- Unit tests: pure functions and hooks.
- Integration tests: component behavior.
- E2E tests: user flows.

Test priorities:
- User-visible behavior.
- Edge cases.
- Error states.
- Accessibility.

## 14. Anti-Patterns

- Do not prop drill deeply; use context.
- Do not build giant components; split them smaller.
- Do not use `useEffect` for everything; prefer server components where appropriate.
- Do not optimize prematurely; profile first.
- Do not use index as key; use a stable unique ID.

## 15. File Structure

Use a clear file structure that separates components, hooks, utilities, and types. Reference the project's existing conventions or a standard React file layout as a guide.

## When to Use

- Writing new React components or pages.
- Reviewing code for performance issues.
- Refactoring components with too many props or re-renders.
- Debugging "why is this slow?" or "why does this re-render?".
- Building reusable component libraries.
- Code review before merging.

## Limitations

- Use this skill only when the task clearly matches the scope described above.
- Do not treat the output as a substitute for environment-specific validation, testing, or expert review.
- Stop and ask for clarification if required inputs, permissions, safety boundaries, or success criteria are missing.
