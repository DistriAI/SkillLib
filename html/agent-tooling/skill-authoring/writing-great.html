# Writing Great Skills

A skill is a promise: given a request, produce a professional output reliably. The goal is **predictability** — the agent taking the same process every run.

## 1. Design Principles

### Invocation Strategy
Decide how the skill will be triggered:
- **Model-Invoked**: The agent can fire it autonomously. Requires a rich `description` with trigger phrases. Costs **context load** (description is always in context).
- **User-Invoked**: Only the user can trigger it by name. Set `disable-model-invocation: true`. Zero context load, but costs **cognitive load** (user must remember it exists).

*Rule: Use model-invocation only if the agent must reach the skill on its own or another skill must reach it. Otherwise, make it user-invoked.*

### Information Hierarchy
Structure content based on how immediately the agent needs it:
1. **In-skill steps**: Ordered actions in `SKILL.md`. Each must have a checkable **completion criterion**.
2. **In-skill reference**: Definitions/rules in `SKILL.md` consulted on demand.
3. **External reference**: Content pushed to separate files (e.g., `GLOSSARY.md`) via **context pointers**. Use **progressive disclosure** to keep `SKILL.md` legible.

## 2. Anatomy of a SKILL.md

### Frontmatter
```yaml
---
name: kebab-case-name
description: "<What it does> + <Trigger phrases> + <Output promise>"
---
```
- **Description**: The most important line. Front-load the leading word. List distinct **branches** (triggers). Avoid synonyms that duplicate a single branch.

### Body Structure
1. **Value Proposition**: One sentence on the skill's value.
2. **Inputs**: What to ask the user, or how to infer/label assumptions if missing.
3. **Process/Steps**: Ordered actions. If the skill is reference-only, list the rules clearly.
4. **Output Format**: A concrete template (headers, tables) for the final artifact. Do not just describe it; show the shape.
5. **Quality Controls**: Observable checklist items the output must satisfy.
6. **Anti-Patterns**: Specific failure modes to avoid (e.g., vague outputs, placeholders).

## 3. Authoring Process

1. **Define the Deliverable**: What is the specific output?
2. **Draft Description**: Write trigger phrases as users would speak them. Test: "Would the model choose this over a neighbor?"
3. **Structure Content**: Decide what stays in `SKILL.md` vs. what moves to external files.
4. **Write Steps/Reference**: Ensure steps have checkable completion criteria.
5. **Add Quality Controls & Anti-Patterns**: Target specific failure modes.
6. **Validate**: Check structure and run against a minimal brief to ensure it doesn't demand unnecessary inputs.

## 4. Quality Checklist

- [ ] `name` is kebab-case and matches folder.
- [ ] Description has distinct triggers and output promise.
- [ ] No `TODO` or placeholders in final file.
- [ ] Triggers are distinct from neighboring skills.
- [ ] Completion criteria are checkable and exhaustive.
- [ ] Context load is minimized (progressive disclosure used where appropriate).
