# Changelog Generator

This skill transforms technical git commits into polished, user-friendly changelogs. It supports two primary modes: a prompt-based mode for general use and a script-based mode for automated CI/CD pipelines using Conventional Commits.

## When to Use

- Preparing release notes for a new version.
- Automating changelog generation in CI/CD.
- Documenting changes for customers or app store submissions.
- Enforcing commit message standards.

## Workflow

### 1. Determine Mode

- **Script Mode**: Use if the repository uses Conventional Commits and you have access to `scripts/generate_changelog.py`.
- **Prompt Mode**: Use for general repositories or when manual curation is preferred.

### 2. Gather Inputs

- **Commits**: `git log` output, commit range, or raw commit messages.
- **Version**: Target version number (e.g., 2.4.0).
- **Date**: Release date.
- **Audience**: Developers, end-users, or internal team.
- **Scope**: Full product or specific package/module.

### 3. Process Commits

**Script Mode:**
```bash
python3 scripts/generate_changelog.py \
  --from-tag v1.3.0 \
  --to-tag v1.4.0 \
  --next-version v1.4.0 \
  --format markdown
```

**Prompt Mode:**
- Scan git history for the specified range.
- Categorize commits into: Added, Changed, Fixed, Deprecated, Removed, Security, Breaking Changes.
- Translate technical commit messages into user-friendly language.
- Filter out internal commits (refactoring, tests, chore).

### 4. Format Output

Follow Keep a Changelog conventions:

```markdown
## [X.Y.Z] — YYYY-MM-DD

### Breaking Changes ⚠️
- **[Change]:** [Description] — **Migration:** [Action required]

### Added
- [New feature from user perspective]

### Changed
- [Behavior change: before vs. after]

### Fixed
- [Bug description: what was broken, not how it was fixed]

### Security
- [Vulnerability class, not exploit details]
```

**Formatting Rules:**
- Use imperative mood ("Add", "Fix", not "Added", "Fixed").
- Omit empty sections.
- Group related commits into single entries.
- Highlight breaking changes with ⚠️ and migration guidance.

### 5. Quality Checks

- [ ] Breaking changes are at the top with migration instructions.
- [ ] All entries are user-facing (no internal variable names).
- [ ] Related commits are grouped.
- [ ] Version and date header is correct.
- [ ] Empty sections are omitted.
- [ ] Imperative mood is used.

## Conflicts

- **LeoYeAI/openclaw-master-skills**: Requires Conventional Commits and specific Python scripts. If these are not available, fall back to Prompt Mode.
- **mohitagw15856/pm-claude-skills**: Emphasizes a scoring rubric (0-40). Use this rubric to evaluate the final output before delivery.
- **davepoon/buildwithclaude**: General prompt-based approach. Use this as the default when no specific scripts or rubrics are defined.

## Tips

- Run from the git repository root.
- Specify date ranges for focused changelogs.
- Review and adjust the generated changelog before publishing.
- Save output to `CHANGELOG.md` or use `--write` in script mode.
