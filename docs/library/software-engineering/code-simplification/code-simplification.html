# Code Simplification

Simplify code by reducing complexity while preserving exact behavior. The goal is code that is easier to read, understand, modify, and debug.

## When to Use
- After a feature is working and tests pass, but the implementation feels heavier than it needs to be
- During code review when readability or complexity issues are flagged
- When refactoring code written under time pressure or AI-generated code that is over-engineered

## When NOT to Use
- Code is already clean and readable
- You don't understand what the code does yet
- The code is performance-critical and the "simpler" version would be measurably slower

## Required Inputs
- The code to simplify
- What must not change (public API, behavior, performance)
- Test coverage status

## The Process

### Step 1: Understand Before Touching (Chesterton's Fence)
Before changing or removing anything, understand why it exists. Check git blame and history for the original context. If you can't answer why the code is shaped that way, read more context first.

### Step 2: Identify Simplification Opportunities
Scan for these patterns in order of payoff:
1. **Speculative generality** — interfaces with one implementation, parameters always called with the same value, config options no caller sets.
2. **Indirection without insulation** — layers that only forward, wrappers calling one function, factories returning one type.
3. **Dead and duplicate paths** — unreachable branches, local re-implementations of existing utilities.
4. **Cleverness taxing readers** — nested ternaries, reduces that should be loops, regexes doing multiple jobs.
5. **Flatten control flow** — guard clauses over nested ifs, early returns over else-pyramids.

### Step 3: Apply Simplifications
- Preserve behavior exactly: all inputs, outputs, side effects, and error behavior must remain identical.
- Follow project conventions: match the codebase's style for imports, naming, and error handling.
- Prefer clarity over cleverness: explicit code is better than compact code when the compact version requires a mental pause.
- Maintain balance: don't inline too aggressively, combine unrelated logic, or optimize for line count.
- Scope to what changed: avoid drive-by refactors of unrelated code.
- One hunt-class per pass where the code is load-bearing: remove speculation, verify; then collapse indirection, verify.

### Step 4: Verify
- Run the full relevant test suite before AND after simplification.
- If coverage is thin over the code being simplified, add pinning tests first.
- For exported/shared code, check callers across the codebase.

## Output Format

### Simplification: [target]

**Verification:** [suite/build run before → after: identical] · pinning tests added: [n or none-needed because…]

**Removal ledger**
| What was removed/flattened | Class | Why safe | Future foreclosed (honest) |
|---|---|---|---|

**Kept deliberately:** [the weird-but-load-bearing bits, with their Chesterton evidence]
**Size:** [LOC/complexity before → after]

## Quality Checks
- [ ] Full verification ran before and after — identical behaviour, evidenced
- [ ] Thinly-tested code got pinning tests before simplification
- [ ] Every removal states the future it forecloses
- [ ] Strange code was history-checked before deletion
- [ ] The result is simpler for a READER, not just shorter

## Anti-Patterns
- Do not simplify and change behaviour in one pass
- Do not delete weirdness without checking why it's weird
- Do not confuse terse with simple
- Do not remove flexibility that's actually on the roadmap
- Do not skip the ledger
