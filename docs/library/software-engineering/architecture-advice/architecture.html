# Architecture Advisor

Use this skill when planning code organization, system design, or refactoring direction.

## Workflow

1. Identify scope: prototype, small game, long-lived project, or general system.
2. Define the core loop or primary requirements and the minimum systems needed.
3. Recommend the smallest architecture that fits the scope.
4. Separate concerns:
   - scene/bootstrap or entry-point layer
   - domain/business logic
   - data/config assets
   - view/presentation layer
5. Call out what should stay simple now versus what is worth abstracting.

## Unity-Specific Guidance

- Prefer thin MonoBehaviour scripts as composition bridges.
- Put reusable gameplay rules in plain C# classes when possible.
- Use ScriptableObject for authored config and shared static data, not as a default dump for runtime state.
- Keep dependencies explicit. Avoid hidden global state unless the project size clearly justifies a small service layer.
- Favor simple module boundaries over framework-heavy architecture.

### Make startup order explicit

- Use one Bootstrap script as the single entry point that owns initialization and calls sub.Init() on managers it creates.
- Prefer pull over push: subscribers call source.GetValue() on demand or subscribe to events.
- Reserve [DefaultExecutionOrder(n)] for load-bearing singletons only. If more than 3-4 scripts need it, the architecture is wrong.

### Make update preconditions explicit

- Every Update/LateUpdate/FixedUpdate should open with guard clauses that early-return when the system is not ready.
- Prefer the cheapest check first: construction-time, dependency-level, then gameplay-state.

## General System Design

- Record significant decisions as ADRs with context, options, and rationale.
- Evaluate trade-offs for each decision and consider simpler alternatives.
- Apply a system design checklist covering scalability, reliability, observability, and security.
- Choose patterns (microservices, event-driven, layered, hexagonal) based on requirements, not fashion.

## Output Format

Structure the advice as:

- Project tier: prototype / small-game / long-lived / general system
- Recommended modules: 3-7 modules with one-line responsibilities
- Scene/bootstrap or entry-point plan: where composition and initialization happen
- Data ownership: what belongs in scene objects, ScriptableObjects, or pure classes
- Communication rules: direct refs, interfaces, events, or commands
- Performance risks: only the hot paths that matter
- Do now / skip now: avoid over-engineering
- ADRs: list significant decisions with trade-off summaries

## Validation Checklist

Before finalizing architecture:

- [ ] Requirements clearly understood
- [ ] Constraints identified
- [ ] Each decision has trade-off analysis
- [ ] Simpler alternatives considered
- [ ] ADRs written for significant decisions
- [ ] Team expertise matches chosen patterns

## Guardrails

- Do not start from a giant reusable framework unless the project truly needs it.
- Do not add layers just to satisfy textbook SOLID wording.
- Prefer a small architecture that can grow, not an impressive one that slows iteration.
- Stop and ask for clarification if required inputs, permissions, safety boundaries, or success criteria are missing.
