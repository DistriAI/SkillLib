# Executing Plans

## When to Use
- You have a written implementation plan to execute.
- The plan has verifiable steps and a completion test.

## Setup
1. Read the plan file and the associated spec.
2. Review critically: identify questions, concerns, or stale assumptions.
3. If concerns exist, raise them with your human partner before starting.
4. Set up an isolated workspace (e.g., git worktree) if the plan requires it.
5. Initialize a visible execution log (ledger or step-by-step log).

## Execution Model
Choose the execution cadence based on user preference or project contract:
- **Continuous (Inline):** Execute all tasks without pausing. Use a ledger to track state. Perform one final whole-branch review at the end.
- **Batched:** Execute tasks in batches (default: 3 tasks or user-specified size). Report progress and verification output after each batch. Wait for feedback before continuing.

## Per-Task Process
1. Mark the task as in-progress.
2. Execute each step exactly as written in the plan.
3. Run every specified verification. Record the result.
4. If reality disagrees with the plan, classify the divergence:
   - **Detail:** Intent holds, mechanics differ. Note in log, continue.
   - **Deviation:** Approach must change. Amend plan visibly, state why, continue.
   - **Invalidation:** Goal or stop condition hit. STOP. Report to human. Replan.
5. Commit as specified in the plan.
6. Mark the task as complete in the log.

## Stop Conditions
Stop and ask for help when:
- An irreversible or destructive operation is required.
- A security-sensitive action is required.
- A side effect outside the worktree (merge, push, publish) is required.
- A blocker prevents progress (missing dependency, unclear instruction, repeated verification failure).
- The plan is fundamentally broken.

## Completion
1. Run the plan's DONE test.
2. If using continuous execution: perform a final whole-branch review. Fix critical/important issues with RED→GREEN cycles. Ledger minor issues.
3. If using batched execution: confirm all batches are approved.
4. Write a plan feedback note: what the plan got wrong, which estimates were off, which risks fired.
5. Use the finishing-a-development-branch skill (or equivalent) to complete the work.

## Conflicts
- **obra/superpowers** mandates continuous execution with a final review; **sickn33** and **LeoYeAI** mandate batched execution with per-batch reviews. **mohitagw15856** mandates scheduled checkpoints and a specific divergence classification. The combined instruction allows the user to choose the cadence, but requires the divergence classification and feedback note from all models.
