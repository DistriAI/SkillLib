# TDD Workflow

Use this skill when implementing a feature, fixing a bug, or refactoring code and you want tests to lead. Run one small red-green-refactor cycle at a time; do not jump ahead to untested code.

## Required Inputs

Ask for these only if they are not already provided:

- The behavior to build, stated as observable behavior (input → expected output).
- The stack: language, test framework/runner, and where tests live.
- The seam: the function/module/endpoint under test, and any collaborators to fake/mock.
- Edge cases: errors, empty inputs, boundaries, and other conditions that matter.

## TDD Cycle

For each behavior, run one cycle at a time, smallest first:

1. 🔴 Red — Write a single failing test that asserts one observable behavior. The test must fail before any implementation exists. The test name should describe the expected behavior.
2. 🟢 Green — Write the minimal code to make exactly that test pass. No extra features, no speculative generality, no optimization.
3. 🔵 Refactor — Clean up naming, duplication, structure, or complexity while all tests stay green. Skip if nothing is needed. Commit after each green and after each refactor.
4. Run — Execute the test(s) and confirm the expected passing state.

End each cycle by identifying the next red test.

## Three Laws of TDD

1. Write production code only to make a failing test pass.
2. Write only enough test to demonstrate failure.
3. Write only enough code to make the test pass.

## Test Design

- Follow the AAA pattern: Arrange test data, Act on the code under test, Assert the expected outcome.
- Prefer one assertion per test, or one behavior per test.
- Test observable behavior, not implementation details.
- Make each test self-sufficient: include all setup, execution, and teardown so it can run in isolation.
- Duplication over factoring: duplicate setup code in tests when it keeps each test clear and independent.
- Plan for failure: write tests assuming they will fail and require debugging; make logic explicit.

## Test Prioritization

1. Happy path
2. Error cases
3. Edge cases
4. Performance

## When to Use TDD

- New feature: high value.
- Bug fix: high value; write the failing test first.
- Complex logic: high value.
- Exploratory work: low value; spike first, then apply TDD.
- UI layout: low value.

## Anti-Patterns

- Do not write the implementation first and the test after.
- Do not write many tests and then all the code; one red→green→refactor cycle at a time.
- Do not over-build in green; only enough to pass the current test.
- Do not test implementation details.
- Do not skip the refactor step when there is obvious duplication or a bad name.
- Do not skip the red phase; watch the test fail first.

## R / testthat Specifics

When the stack is R with testthat:

- Initialize testthat Edition 3 with `usethis::use_testthat(3)` and ensure `Config/testthat/edition: 3` in DESCRIPTION.
- Create test files with `usethis::use_test("function_name")` or create source and test together with `usethis::use_r("function_name")` and `usethis::use_test("function_name")`.
- During development, prefer `devtools::load_all()` over `library()` to expose unexported functions and attach testthat.
- Target at least 80% coverage overall; aim for 100% coverage on statistical calculations and data validation.
- Use `test_that()` for unit and integration tests; use `describe()`/`it()` for BDD-style tests when appropriate.
- Use snapshot tests for complex outputs or error messages; review and accept snapshots with `testthat::snapshot_review()` and `testthat::snapshot_accept()`.
- Replace deprecated patterns: remove `context()`, use `expect_equal(x, y, ignore_attr = TRUE)` instead of `expect_equivalent()`, use `local_mocked_bindings()` instead of `with_mock()`, and use `expect_s3_class()` instead of `expect_is()`.

## Multi-Agent Pattern (Optional)

When using multiple agents:

- Agent A writes the failing tests (RED).
- Agent B implements the minimal code to pass (GREEN).
- Agent C optimizes and refactors (REFACTOR).

## Quality Checks

- Behaviors are listed and ordered simplest-first; each cycle tests one behavior.
- The red step writes a genuinely failing test before any implementation.
- The green step is the minimal code to pass, with no untested extra functionality.
- Refactoring happens only on green, with tests as the safety net.
- Edge and error cases each get their own cycle, not bolted onto the happy path.
