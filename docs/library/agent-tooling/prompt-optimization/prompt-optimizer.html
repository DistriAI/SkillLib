# Prompt Optimizer

## Overview

This skill combines three complementary approaches to prompt optimization:
1. **EARS Transformation** - Convert vague feature requests into normative, testable requirements using EARS syntax and domain theory grounding.
2. **Eval-Driven Engineering** - Capture a contract, inventory external context, choose a model strategy, and iteratively optimize using evals.
3. **Diagnosis & Rewrite** - Identify specific failure modes in an existing prompt and produce a full rewrite with a test set.

Select the primary approach based on the input:
- **Vague feature request** (e.g., "build a dashboard") → Use EARS Transformation.
- **Existing agent/system prompt** (e.g., "optimize this system prompt") → Use Eval-Driven Engineering.
- **Failing prompt with symptoms** (e.g., "this prompt gives inconsistent output") → Use Diagnosis & Rewrite.

## When to Use

Apply when:
- User provides vague feature requests or requirements lacking triggers or measurable outcomes.
- User asks to optimize, improve, or refine an existing prompt.
- User reports a prompt that produces inconsistent, wrong, or hallucinated results.
- User asks to port a prompt between model families.

## Workflow

### Step 1: Classify the Task

Determine the task type:
- **New requirement**: Vague feature request → EARS path.
- **Refine existing prompt**: Agent/system prompt → Eval-Driven path.
- **Debug failing prompt**: Prompt with reported symptoms → Diagnosis path.
- **Port prompt**: Between model families → Eval-Driven path with model-family notes.

### Step 2: Capture Contract (Eval-Driven & Diagnosis paths)

Record before editing:
- Task type: new, refine, port, or debug.
- Target model family and snapshot, if known.
- Prompt surface: system, developer, user, tool descriptions, examples, schemas.
- Objective and non-goals.
- Inputs, tools, and external files available.
- Required output shape.
- Success criteria and failure cases.
- Hard constraints: latency, verbosity, safety, budget, tool use, style.

If success criteria or examples are missing, create a small eval set first.

### Step 3: Analyze Original Requirement or Prompt

**For EARS path:**
Identify weaknesses:
- Overly broad, missing triggers, ambiguous actions, no constraints.

**For Eval-Driven path:**
Inventory external context by exact path:
- Agent rules, specs, policies, examples.
- Reference stable files by repo-relative path instead of copying them.
- Mark whether a file is loaded, referenced, or out of scope.

**For Diagnosis path:**
Identify specific failure modes:
- Inconsistent format → no explicit output contract.
- Hallucinated details → asked to answer without grounding.
- Ignores an instruction → buried mid-paragraph.
- Refusals → unclear constraints or safety conflicts.

### Step 4: Apply Transformation

**EARS Transformation:**
Convert requirements to EARS patterns:
1. Ubiquitous: `The system shall <action>`
2. Event-driven: `When <trigger>, the system shall <action>`
3. State-driven: `While <state>, the system shall <action>`
4. Conditional: `If <condition>, the system shall <action>`
5. Unwanted behavior: `If <condition>, the system shall prevent <unwanted action>`

Identify domain theories and apply relevant frameworks:
- Productivity → GTD, Pomodoro, Eisenhower Matrix
- Behavior Change → BJ Fogg Model, Atomic Habits
- UX Design → Hick's Law, Fitts's Law, Gestalt Principles
- Security → Zero Trust, Defense in Depth, Privacy by Design

**Eval-Driven Optimization:**
1. Baseline the current prompt on the same eval slice.
2. Cluster failures by root cause.
3. Write concrete edit criticisms.
4. Generate two to four candidates: minimal-diff repair, structure-first rewrite, examples-first variant, provider adapter.
5. Compare candidates on the same cases.
6. Keep a short optimization log.
7. Validate the winner on holdout cases.
8. Stop on plateau, oscillation, overfit, excessive cost, or non-prompt bottleneck.

**Diagnosis & Rewrite:**
Apply levers that match the diagnosed failure:
- Role + task in the first lines.
- Explicit output contract (structure/schema + a short example).
- Grounding rules ("answer only from X; if unknown, say so").
- Constraints stated as rules not prose.
- 1-3 few-shot examples when the task needs a demonstrated pattern.

### Step 5: Generate Enhanced Prompt

Structure using the standard framework:

```markdown
# Role
[Specific expert role with domain expertise]

## Skills
- [Core capability 1]
- [Core capability 2]
[List 5-8 skills aligned with domain theories]

## Workflows
1. [Phase 1] - [Key activities]
2. [Phase 2] - [Key activities]
[Complete step-by-step process]

## Examples
[Concrete examples with real data, not placeholders]

## Formats
[Precise output specifications:
- File types, structure requirements
- Design/styling expectations
- Technical constraints
- Deliverable checklist]
```

**Quality criteria:**
- Role specificity: "Product designer specializing in time management apps" > "Designer"
- Theory grounding: Reference frameworks explicitly
- Actionable workflows: Clear inputs/outputs and decision points
- Concrete examples: Real data, not "Example 1", "Example 2"
- Measurable formats: Specific requirements, not "good design"

### Step 6: Present Optimization Results

Output in structured format:

```markdown
## Original Requirement or Prompt
[User's input]

**Identified Issues:**
- [Issue 1: e.g., "Lacks specific trigger conditions"]
- [Issue 2: e.g., "No measurable success criteria"]

## Transformation
[EARS-formatted requirements, eval-driven changes, or diagnosis table]

## Domain & Theories (EARS path)
**Primary Domain:** [e.g., Authentication Security]

**Applicable Theories:**
- **[Theory 1]** - [Brief relevance]
- **[Theory 2]** - [Brief relevance]

## Enhanced Prompt
[Complete Role/Skills/Workflows/Examples/Formats prompt or full rewrite]

## Test Set
[3-5 concrete inputs including edge cases and negative cases with expected outputs]

## What Changed and Why
[Short bullet list mapping each edit to the symptom it addresses]

## Residual Risks
[Any remaining limitations or failure modes]
```

## Conflicts

- **daymade/claude-code-skills** uses EARS syntax and domain theory grounding (GTD, BJ Fogg, Gestalt) to transform vague feature requests into normative specifications. This is not present in the other two copies.
- **getsentry/skills** uses an eval-driven meta-optimization loop with model-family notes, external context inventory, and candidate generation/comparison. This is not present in the other two copies.
- **mohitagw15856/pm-claude-skills** uses a diagnosis-first approach that identifies specific failure modes and returns a full rewrite with a diagnosis table and a 3-5 item test set. This is not present in the other two copies.

## Failure Modes

- Editing before defining the eval target.
- Mixing policy, examples, and raw context without boundaries.
- Duplicating rules across layers.
- Putting durable policy in user payloads.
- Asking for chain-of-thought.
- Keeping contradictory legacy instructions.
- Overfitting to one or two examples.
- Retaining examples that no longer improve evals.
- Fixing tool-use failures only in prompt text when tool descriptions or schemas are weak.
- Adding markup that does not reduce ambiguity.
- Using persona as a substitute for behavior rules.
- Returning a critique without the rewritten prompt.
- Piling on every technique at once.
- Adding examples that contradict the instructions.
- Making the prompt longer when the fix is to make instructions clearer and earlier.
- Claiming a fix works without a way to test it.
