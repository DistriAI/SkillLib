# Project Development Methodology

This skill covers the principles for identifying tasks suited to LLM processing, designing effective project architectures, and iterating rapidly using agent-assisted development.

## When to Activate

Activate this skill when the unit of work is a whole project or pipeline:
- Deciding whether an LLM is the right primitive for a task.
- Shaping a multi-stage batch or agent pipeline.
- Estimating tokens, dollar cost, and timelines.
- Choosing between single-agent and multi-agent at the project level.
- Designing structured output at the pipeline contract level.

Do not activate for:
- Per-tool design (use `tool-design`).
- Per-trajectory token-efficiency tactics (use `context-optimization`).
- Agent topology splitting (use `multi-agent-patterns`).

## Core Concepts

### 1. Task-Model Fit Recognition

Evaluate task-model fit before writing any code.

**Proceed when:**
- Synthesis across sources
- Subjective judgment with rubrics
- Natural language output
- Error tolerance
- Batch processing
- Domain knowledge in training

**Stop when:**
- Precise computation
- Real-time requirements
- Perfect accuracy requirements
- Proprietary data dependence
- Sequential dependencies
- Deterministic output requirements

### 2. The Manual Prototype Step

Always validate task-model fit with a manual test before investing in automation.
- Copy one representative input into the model interface.
- Evaluate output quality.
- Answer: Does the model have the knowledge? Can it produce the format? What is the quality baseline? What are the failure modes?

### 3. Pipeline Architecture

Structure LLM projects as staged pipelines. Each stage must be:
- **Discrete**: Clear boundaries.
- **Idempotent**: Re-running produces the same result.
- **Cacheable**: Intermediate results persist.
- **Independent**: Each stage can run separately.

**Canonical Structure:**
```
acquire -> prepare -> process -> parse -> render
```
1. **Acquire**: Fetch raw data.
2. **Prepare**: Transform data into prompt format.
3. **Process**: Execute LLM calls (non-deterministic/expensive).
4. **Parse**: Extract structured data.
5. **Render**: Generate final outputs.

### 4. File System as State Machine

Use the file system to track pipeline state. Each processing unit gets a directory.

```
data/{id}/
├── raw.json         # acquire complete
├── prompt.md        # prepare complete
├── response.md      # process complete
├── parsed.json      # parse complete
```

- **Idempotency**: File existence gates execution.
- **Debugging**: Read intermediate files directly.
- **Re-running**: Delete output file and downstream files.

### 5. Structured Output Design

When LLM outputs must be parsed programmatically:
1. **Section markers**: Explicit headers/prefixes.
2. **Format examples**: Show exactly what output should look like.
3. **Rationale disclosure**: "I will be parsing this programmatically."
4. **Constrained values**: Enumerated options, score ranges.

**Example Prompt:**
```
Analyze the following and provide your response in exactly this format:

## Summary
[Your summary here]

## Score
Rating: [1-10]

Follow this format exactly because I will be parsing it programmatically.
```

Parsing code must handle variations gracefully.
