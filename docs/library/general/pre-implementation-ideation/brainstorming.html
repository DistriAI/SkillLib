# Brainstorming

## Purpose
Use this skill before any creative work to clarify intent, explore options, and validate a direction before implementation.

## 1. Assess Context
- Review existing project files, docs, and recent commits if available.
- Determine if the request is a quick, clear task (e.g., "change color to blue") or if non-trivial details are missing.
- If the task is trivial and clear, proceed directly to execution.
- If the user prefers to skip questions, state significant technical choices in one line and proceed.

## 2. Clarify Intent
- Ask one question at a time to understand purpose, constraints, success criteria, and non-goals.
- Prefer multiple-choice questions when possible, but use open-ended questions to let the user describe their vision in their own words.
- Clarify non-functional requirements (performance, scale, security) and mark assumptions explicitly.
- **Understanding Lock:** Before proposing designs, summarize your understanding (5-7 bullets) and ask for explicit confirmation. Do not proceed until confirmed.

## 3. Explore Options
- **Divergent Phase:** Generate a wide set of ideas (20-40) using distinct strategies (inversion, extremes, transplant, etc.). Avoid judgment during this phase.
- **Convergent Phase:** Define 3-4 selection criteria based on the user's situation. Score ideas coarsely and select a shortlist of 3-5 options, including one "wildcard" high-variance option.
- **Design Approaches:** Propose 2-3 viable design approaches with trade-offs. Lead with your recommendation.

## 4. Present Design
- Present the design in sections of 200-300 words.
- After each section, ask for feedback: "Does this look right so far?"
- Cover architecture, components, data flow, error handling, and testing.
- Maintain a Decision Log recording what was decided, alternatives considered, and why.

## 5. Documentation & Handoff
- Write the validated design to a durable format (e.g., `docs/plans/YYYY-MM-DD-<topic>-design.md`).
- Include the understanding summary, assumptions, decision log, and final design.
- Commit the document to version control.
- **Handoff:** Only after documentation is complete, transition to implementation planning (e.g., invoke a writing-plans skill or create an implementation plan).

## Key Principles
- One question at a time.
- Assumptions must be explicit.
- YAGNI ruthlessly.
- Validate incrementally.
- Do not implement until the design is approved and documented.
