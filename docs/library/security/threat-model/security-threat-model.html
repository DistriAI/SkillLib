# Security Threat Model

Deliver an actionable, evidence-based threat model. Choose the appropriate workflow based on the user's request: **Repository-Grounded** (for codebases) or **Service/Feature STRIDE** (for design reviews).

## Workflow A: Repository-Grounded Threat Model

Use when the user asks to threat model a codebase, path, or repository.

1. **Collect Inputs:**
   - Repo root path and in-scope paths.
   - Intended usage, deployment model, and auth expectations.
   - Use `references/prompt-template.md` for the repository summary and output contract.

2. **Scope and Extract System Model:**
   - Identify components, data stores, and integrations from the repo.
   - Separate runtime behavior from CI/dev tooling.
   - Map in-scope locations to components.

3. **Derive Boundaries and Assets:**
   - Enumerate trust boundaries (protocol, auth, encryption).
   - List risk-driving assets (data, credentials, config).
   - Identify entry points (endpoints, parsers, admin tools).

4. **Calibrate Attacker Capabilities:**
   - Describe realistic attacker capabilities based on exposure.
   - Note non-capabilities to avoid inflated severity.

5. **Enumerate Threats:**
   - Map attacker goals to assets and boundaries.
   - Keep the list small but high-quality.

6. **Prioritize:**
   - Use qualitative likelihood/impact (low/medium/high).
   - Adjust for existing controls.

7. **Validate with User:**
   - Ask 1–3 targeted questions to resolve missing context.
   - Pause for user feedback before finalizing.

8. **Recommend Mitigations:**
   - Distinguish existing from recommended mitigations.
   - Tie mitigations to concrete locations and control types.

9. **Finalize:**
   - Run quality checks (entrypoints covered, boundaries represented).
   - Write to `<repo-or-dir-name>-threat-model.md`.

## Workflow B: Service/Feature STRIDE Threat Model

Use when the user asks for a STRIDE-based model, security design review, or service posture assessment.

1. **Collect Required Inputs:**
   - Service name and description.
   - Architecture overview (components, data flows).
   - Deployment environment (cloud, VPC, Kubernetes, etc.).
   - Data sensitivity (PII, payment, credentials).
   - Existing controls (auth, encryption, WAF).
   - Trust levels (principals: public, authenticated, internal, admin).

2. **Define Scope:**
   - State what is in scope and out of scope.

3. **Create Asset Register:**
   - List assets with description, sensitivity (Critical/High/Medium/Low), and owner.

4. **Map Trust Boundaries:**
   - Create an ASCII diagram of the architecture.
   - List boundaries with auth mechanisms and encryption status.

5. **STRIDE Threat Analysis:**
   - For each component, enumerate threats in STRIDE categories:
     - **S**poofing, **T**ampering, **R**epudiation, **I**nformation Disclosure, **D**enial of Service, **E**levation of Privilege.

6. **Risk Scoring and Mitigation:**
   - Assign risk scores based on likelihood and impact.
   - Recommend mitigation controls.
   - Document residual risk and sign-off.

7. **Output Format:**
   - Produce a structured document with sections: Overview, Asset Register, Trust Boundaries, STRIDE Analysis, Risk Scores, Mitigations, and Residual Risk.

## Conflicts
- **Framework:** Workflow A uses a generic abuse-path approach; Workflow B mandates STRIDE.
- **Input:** Workflow A infers from code; Workflow B requires explicit architecture/deployment details.
- **Output:** Workflow A writes a specific filename based on repo name; Workflow B produces a structured document with specific tables and diagrams.
