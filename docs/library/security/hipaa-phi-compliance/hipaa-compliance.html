# HIPAA Compliance

Implement HIPAA Security, Privacy, and Breach Notification Rule requirements for systems handling ePHI.

## Regulatory Framework

### Security Rule Safeguards
- **Administrative**: Conduct risk analysis, implement risk management, apply sanction policies, review system activity, manage workforce security, and maintain contingency plans (backup, disaster recovery, emergency mode).
- **Physical**: Implement facility access controls, workstation use/security, and device/media controls.
- **Technical**: Enforce unique user identification, emergency access procedures, audit controls, integrity mechanisms, person/entity authentication, and transmission security.

### Privacy & Breach Rules
- **Minimum Necessary**: Limit PHI use/disclosure to the minimum necessary.
- **Individual Rights**: Support access, amendment, accounting of disclosures, and restrictions.
- **Breach Notification**: Notify individuals within 60 days; notify HHS annually (<500 records) or within 60 days (500+); notify media if 500+ individuals in a state/jurisdiction are affected.

## Technical Implementation Checklist

### Encryption
- **At Rest**: Use AES-256. Enable encryption for all data stores (RDS, S3, EBS, DynamoDB, Azure SQL, Storage, Cloud SQL, BigQuery, etc.) using customer-managed keys (KMS/CMK/CMEK).
- **In Transit**: Enforce TLS 1.2+ on all load balancers, API gateways, and database connections. Use mTLS for internal service-to-service communication. Encrypt email containing PHI.
- **Key Management**: Use customer-managed keys, enable annual rotation, restrict access to authorized roles, and audit key usage.

### Access Control
- **Identity**: Enforce MFA for all users accessing PHI. Use unique user accounts (no shared credentials) and federated identity (SSO).
- **Roles**: Apply least privilege. Separate data access from administration. Require just-in-time approval for privileged access.
- **Sessions**: Enforce 15-minute idle timeout. Implement re-authentication for sensitive operations.

## Application-Specific Implementation (Code-Level)

### Audit Logging
- **When to Log**: All PHI views, modifications, deletions, exports, admin actions, failed authentications, and security events.
- **How to Log**: Use dedicated audit utilities (e.g., `logPHIAccess`, `logPHIModification`).
- **Sanitization**: Never log PHI content (e.g., journal text, chat messages). Log only metadata (IDs, word counts, timestamps). Auto-redact fields like `password`, `token`, `content`, `message`.

### Session Security Parameters
- **Timeout**: 15 minutes of inactivity.
- **Max Session**: 8 hours absolute maximum.
- **Lockout**: 5 failed login attempts trigger a 30-minute ban.
- **Passwords**: Minimum 12 characters, mixed case, numbers, and special characters.

### Emergency Access (Break Glass)
- Require written justification for emergency access.
- Create a permanent, enhanced audit record.
- Trigger an alert to the compliance officer.
- Review access within 24 hours.

### Audit Log Retention
- **Minimum**: 6 years.
- **Format**: Raw logs for 1 year, compressed thereafter.
- **Storage**: Secure database table (e.g., `audit_log`).
- **Export**: Encrypted exports for compliance audits.

## Compliance Checklist
- [ ] All PHI access is audit logged.
- [ ] No PHI content in logs (only IDs and metadata).
- [ ] Data access requires authentication and MFA.
- [ ] Admin access has a separate audit trail.
- [ ] Failed access attempts are logged.
- [ ] Data export includes an audit entry.
- [ ] Sensitive fields are encrypted at rest and in transit.
- [ ] Session timeout and lockout policies are enforced.
- [ ] Break-glass access procedures are documented and tested.
