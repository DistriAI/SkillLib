When to use

  • Create clear, concise user stories that combine Mike Cohn's user story format with Gherkin-style acceptance criteria. Use this to translate user needs into actionable development work that focuses on outcomes, ensures shared understanding…

When not to use

  • Pure technical debt or refactoring
  • Stories that are too large
  • Before understanding the user problem
  • Feature specs
  • Tech tasks
  • Feature lists
  • Vague requests without clear outcomes
