accessibility-audit

combined

Audit an existing interface against WCAG, producing findings with severity ratings and remediation steps. Use when you have a design or build to assess now. Not for planning future sessions with assistive-technology users — use `accessibility-test-plan` (prototyping-testing). Generate a WCAG 2.2 accessibility audit checklist and remediation suggestions for any UI or design. Use when asked to audit for accessibility, check WCAG compliance, review a design for a11y issues, or create an accessibility remediation plan. Produces a prioritised checklist with pass/fail assessments and specific fixes.

When to use

  • Audit existing interface against WCAG
  • Check WCAG compliance
  • Review design for a11y issues
  • Create accessibility remediation plan
  • Assess visual, motor, cognitive, and screen reader accessibility
  • Compute contrast ratios
  • Identify barriers and provide remediation guidance

When not to use

  • Planning future sessions with assistive-technology users

Skill page

Conflict

The two skills overlap in purpose (WCAG 2.2 accessibility audit with remediation) but each contains material steps the other lacks. The first defines a severity scale (Critical/Major/Minor/Enhancement) and a concise issue format, while the second provides a detailed checklist, a required-inputs protocol, a programmatic contrast helper (notugly), and a structured output template with pass/fail assessments. They also disagree on severity labels (Major vs Moderate) and on whether to ask questions when inputs are missing, so crowning one would hide a real alternative.
